# ГЛАВА 1. АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ И ПОСТАНОВКА ЗАДАЧИ

## 1.1. Характеристика предметной области

Магазин кондитерских изделий представляет собой предприятие розничной торговли, специализирующееся на продаже сладостей собственного производства или от поставщиков. Особенностью данной предметной области является:

1. **Широкий ассортимент продукции** — кондитерские изделия могут включать торты, пирожные, печенье, конфеты, десерты и другие виды сладостей.

2. **Индивидуальный подход к заказам** — многие клиенты заказывают продукцию к конкретным событиям (дни рождения, свадьбы, корпоративные мероприятия), что требует учёта пожеланий по оформлению, составу и срокам изготовления.

3. **Особые требования к составу** — современные потребители всё чаще обращают внимание на наличие аллергенов (орехи, глютен, молочные продукты), диетические характеристики (веганская продукция) и натуральность ингредиентов.

4. **Сезонность спроса** — продажи кондитерских изделий имеют выраженную сезонность, связанную с праздниками (Новый год, 8 Марта, День святого Валентина и др.).

5. **Короткий срок хранения** — большинство кондитерских изделий имеют ограниченный срок годности, что требует оперативного управления запасами.

### Основные бизнес-процессы магазина

1. **Приём заказов от клиентов**:
   - Консультация клиента по ассортименту;
   - Подбор продукции согласно требованиям (праздник, диетические ограничения, предпочтения по ингредиентам);
   - Оформление заказа с указанием контактных данных клиента.

2. **Обработка заказов**:
   - Фиксация заказа в системе учёта;
   - Передача информации о заказе в производство (для изделий на заказ);
   - Подготовка продукции к выдаче.

3. **Учёт продаж**:
   - Регистрация факта продажи;
   - Фиксация состава заказа (товары, количество, цены);
   - Обновление остатков на складе.

4. **Аналитика продаж**:
   - Анализ популярности товаров;
   - Выявление тенденций спроса;
   - Прогнозирование потребности в сырье;
   - Оценка эффективности маркетинговых мероприятий.

### Проблемы традиционного подхода

При ручном управлении продажами возникают следующие проблемы:

- **Потеря информации** — бумажные журналы заказов могут быть утеряны или повреждены;
- **Ошибки при вводе данных** — человеческий фактор приводит к ошибкам в расчётах и оформлении;
- **Низкая скорость обслуживания** — ручной поиск информации и оформление заказов занимают много времени;
- **Отсутствие аналитики** — без автоматизированной системы сложно собирать и анализировать данные о продажах;
- **Сложность учёта индивидуальных требований** — отслеживание пожеланий клиентов по составу и оформлению затруднено.

## 1.2. Анализ существующих решений

На современном рынке представлено множество решений для автоматизации торговли, которые можно разделить на несколько категорий:

### 1. Универсальные системы учёта (1С, МойСклад, RetailCRM)

**Преимущества:**
- Широкий функционал для управления торговлей;
- Интеграция с бухгалтерскими системами;
- Поддержка различных видов оборудования (кассовые аппараты, сканеры штрих-кодов).

**Недостатки:**
- Высокая стоимость лицензий и внедрения;
- Избыточный функционал для небольшого магазина;
- Сложность настройки под специфику кондитерских изделий;
- Ограниченные возможности для кастомизации аналитических отчётов.

### 2. Специализированные решения для общепита (iiko, R-Keeper)

**Преимущества:**
- Учёт специфики пищевых производств;
- Управление рецептурами и технологическими картами;
- Интеграция с кухонным оборудованием.

**Недостатки:**
- Ориентация на рестораны и кафе, а не на розничную торговлю;
- Высокая стоимость;
- Сложность в использовании для небольших магазинов.

### 3. Онлайн-конструкторы интернет-магазинов (Tilda, InSales, Shopify)

**Преимущества:**
- Быстрый запуск онлайн-витрины;
- Готовые шаблоны дизайна;
- Встроенные платёжные системы.

**Недостатки:**
- Ограниченная гибкость в настройке функционала;
- Ежемесячная абонентская плата;
- Недостаточные возможности для глубокой аналитики;
- Сложности с учётом индивидуальных характеристик продукции (аллергены, ингредиенты).

### Выводы по анализу

Проведённый анализ показал, что существующие решения либо избыточны по функционалу и стоимости для небольшого магазина кондитерских изделий, либо не учитывают специфику данной предметной области (учёт ингредиентов, аллергенов, привязка к праздникам). Это обосновывает необходимость разработки специализированного решения, адаптированного под конкретные требования заказчика.

## 1.3. Обоснование выбора средств разработки

### Выбор архитектуры приложения

Для реализации системы была выбрана **клиент-серверная архитектура** с разделением на frontend (клиентская часть) и backend (серверная часть). Такое разделение обеспечивает:

- **Масштабируемость** — возможность независимого развития клиентской и серверной частей;
- **Гибкость** — возможность создания нескольких клиентов (веб-приложение, мобильное приложение) для одного backend;
- **Безопасность** — вся бизнес-логика сосредоточена на сервере, что снижает риски утечки данных;
- **Производительность** — нагрузка распределяется между клиентом и сервером.

### Выбор технологий для Backend

Для реализации серверной части был выбран **фреймворк FastAPI** на языке программирования **Python**.

**Обоснование выбора FastAPI:**

1. **Высокая производительность** — FastAPI является одним из самых быстрых Python-фреймворков благодаря использованию Starlette и Pydantic.

2. **Асинхронная поддержка** — встроенная поддержка async/await позволяет эффективно обрабатывать множество одновременных запросов.

3. **Автоматическая документация** — FastAPI автоматически генерирует интерактивную API-документацию (Swagger UI, ReDoc), что упрощает разработку и тестирование.

4. **Валидация данных** — использование Pydantic обеспечивает строгую валидацию входных и выходных данных с подробными сообщениями об ошибках.

5. **Типизация** — поддержка type hints улучшает читаемость кода и помогает выявлять ошибки на этапе разработки.

6. **Простота изучения** — интуитивно понятный синтаксис и обширная документация ускоряют процесс разработки.

**Обоснование выбора Python:**

- Широкая экосистема библиотек для работы с данными;
- Простота написания и поддержки кода;
- Кроссплатформенность;
- Большое сообщество разработчиков.

### Выбор базы данных

Для хранения данных была выбрана **реляционная база данных SQLite**.

**Обоснование выбора SQLite:**

1. **Простота развёртывания** — SQLite не требует установки отдельного сервера СУБД, база данных хранится в одном файле.

2. **Лёгкость** — минимальные требования к ресурсам, что важно для небольших проектов.

3. **Надёжность** — несмотря на простоту, SQLite обеспечивает ACID-совместимость и целостность данных.

4. **Достаточный функционал** — поддержка SQL-запросов, транзакций, индексов полностью покрывает потребности проекта.

5. **Переносимость** — файл базы данных легко переносить между системами.

*Примечание: При росте нагрузки система может быть мигрирована на PostgreSQL или MySQL с минимальными изменениями в коде.*

### Выбор технологий для Frontend

Для клиентской части было разработано веб-приложение с использованием современных технологий:

- **HTML5/CSS3** — базовые технологии вёрстки;
- **JavaScript (ES6+)** — язык программирования для клиентской логики;
- **Фреймворк для UI** — использование компонентного подхода для создания переиспользуемых элементов интерфейса.

**Обоснование выбора веб-интерфейса:**

- Кроссплатформенность — доступ с любого устройства с браузером;
- Отсутствие необходимости установки дополнительного ПО;
- Возможность быстрого обновления интерфейса;
- Удобство интеграции с backend через REST API.

### Выбор способа развёртывания

Для деплоя приложения была выбрана облачная платформа **Amvera** (российский аналог Heroku).

**Преимущества Amvera:**

- Простота развёртывания — достаточно отправить код в Git-репозиторий;
- Автоматическое масштабирование;
- Бесплатный тариф для небольших проектов;
- Российская юрисдикция — соответствие требованиям законодательства о персональных данных.

## 1.4. Постановка задачи

На основе анализа предметной области и существующих решений были сформулированы следующие требования к разрабатываемой системе:

### Функциональные требования

1. **Каталог продукции**:
   - Отображение списка всех кондитерских изделий;
   - Фильтрация по категориям, праздникам, ингредиентам;
   - Фильтрация по диетическим характеристикам (без орехов, без глютена, без молочных продуктов, веган);
   - Сортировка по цене;
   - Поиск по названию.

2. **Оформление заказов**:
   - Добавление товаров в корзину;
   - Изменение количества товаров;
   - Ввод контактных данных клиента;
   - Добавление комментария к заказу;
   - Отправка заказа на сервер.

3. **Административная панель**:
   - Авторизация администратора;
   - Просмотр списка заказов;
   - Детальная информация по каждому заказу;
   - Доступ к аналитическим отчётам.

4. **Система аналитики**:
   - Отчёт по популярным товарам;
   - Анализ продаж по группам ингредиентов;
   - Анализ продаж по праздникам;
   - Анализ продаж по диетическим характеристикам;
   - Динамика продаж по месяцам;
   - Статистика использования фильтров пользователями;
   - Выявление непопулярных товаров.

### Нефункциональные требования

1. **Производительность**:
   - Время отклика API не более 500 мс;
   - Поддержка до 100 одновременных пользователей.

2. **Безопасность**:
   - Защита административной панели паролем;
   - Валидация всех входных данных;
   - Защита от SQL-инъекций.

3. **Юзабилити**:
   - Интуитивно понятный интерфейс;
   - Адаптивный дизайн для мобильных устройств;
   - Минимальное количество кликов для оформления заказа.

4. **Надёжность**:
   - Сохранение данных о заказах;
   - Резервное копирование базы данных;
   - Обработка ошибок с понятными сообщениями.

### Ограничения

- Бюджет разработки — минимальный (используются бесплатные инструменты и платформы);
- Срок разработки — один учебный семестр;
- Отсутствие интеграции с платёжными системами (на данном этапе);
- Отсутствие интеграции с системами складского учёта.
