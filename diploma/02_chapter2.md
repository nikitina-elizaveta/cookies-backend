## 2.1. Проектирование базы данных

### Концептуальная модель данных

Проектирование базы данных началось с анализа предметной области и выделения основных сущностей и связей между ними. В результате были определены следующие ключевые сущности:

1. **Products (Продукция)** — каталог кондитерских изделий.
2. **Category (Категории)** — классификация продукции по видам.
3. **Difficulty_Level (Уровни сложности)** — характеристика сложности изготовления изделий.
4. **Ingredients (Ингредиенты)** — справочник компонентов, используемых в производстве.
5. **Product_Ingredients (Состав продукции)** — связь между продукцией и ингредиентами.
6. **Customers (Клиенты)** — информация о покупателях.
7. **Sale (Продажи)** — записи о совершённых продажах.
8. **Magazine_Sales (Состав продаж)** — детализация заказов по товарам.
9. **Occasions (Праздники)** — справочник событий, к которым приурочена продукция.
10. **Product_Occasion (Привязка к праздникам)** — связь между продукцией и праздниками.
11. **FilterEvents (События фильтрации)** — логирование действий пользователей по фильтрации.
12. **Calorie_Level (Уровни калорийности)** — классификация по калорийности.

### Логическая модель данных

Ниже приведено подробное описание каждой таблицы базы данных.

#### Таблица Category

Хранит информацию о категориях кондитерских изделий.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_category | INTEGER | Уникальный идентификатор категории | PRIMARY KEY |
| category_name | CHAR(50) | Название категории | NOT NULL |
| parent_category_name | CHAR(50) | Название родительской категории | NOT NULL |

**Обоснование:** Категория позволяет группировать продукцию (например, "Торты", "Пирожные", "Печенье"). Поле parent_category_name поддерживает иерархическую структуру категорий.

#### Таблица Difficulty_Level

Содержит информацию об уровнях сложности изготовления изделий.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| difficulty_level | INTEGER | Уровень сложности | PRIMARY KEY |
| difficulty_name | CHAR(50) | Название уровня | NOT NULL |
| price | DOUBLE | Базовая цена для уровня | CHECK (price > 0) |

**Обоснование:** Разделение по уровням сложности позволяет дифференцировать цены и учитывать трудозатраты на изготовление.

#### Таблица Products

Основная таблица, хранящая информацию о кондитерских изделиях.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_product | INTEGER | Уникальный идентификатор товара | PRIMARY KEY |
| difficulty_level | INTEGER | Ссылка на уровень сложности | FOREIGN KEY → Difficulty_Level |
| id_category | INTEGER | Ссылка на категорию | FOREIGN KEY → Category |
| name | CHAR(100) | Название изделия | NOT NULL |
| price | REAL | Цена за единицу | |
| has_nuts | INTEGER | Флаг наличия орехов | DEFAULT 0 |
| has_gluten | INTEGER | Флаг наличия глютена | DEFAULT 1 |
| has_dairy | INTEGER | Флаг наличия молочных продуктов | DEFAULT 1 |
| is_vegan | INTEGER | Флаг веганской продукции | DEFAULT 0 |
| image | TEXT | URL изображения | |
| description | TEXT | Описание изделия | |
| weight | TEXT | Вес изделия | |
| has_artificial_flavorings | INTEGER | Флаг искусственных ароматизаторов | DEFAULT 0 |

**Обоснование диетических флагов:** Современные потребители всё чаще обращают внимание на состав продукции. Поля has_nuts, has_gluten, has_dairy, is_vegan, has_artificial_flavorings позволяют реализовывать фильтрацию для людей с аллергиями, непереносимостью определённых продуктов или особыми dietary-предпочтениями.

#### Таблица Ingredients

Справочник ингредиентов, используемых при производстве.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_ingredients | INTEGER | Уникальный идентификатор ингредиента | PRIMARY KEY |
| name | CHAR(50) | Название ингредиента | NOT NULL |
| portion | CHAR(50) | Размер порции | NOT NULL |
| calories | INTEGER | Калорийность на порцию | NOT NULL |
| price | DOUBLE | Цена за порцию | CHECK (price > 0) |
| ingredient_group | TEXT | Группа ингредиента | |

**Обоснование:** Группировка ингредиентов (ingredient_group) позволяет анализировать продажи по типам компонентов (например, "шоколад", "фрукты", "орехи").

#### Таблица Product_Ingredients

Связующая таблица многие-ко-многим между Products и Ingredients.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_product | INTEGER | Ссылка на продукт | PRIMARY KEY, FOREIGN KEY → Products |
| id_ingredients | INTEGER | Ссылка на ингредиент | PRIMARY KEY, FOREIGN KEY → Ingredients |
| quantity | DOUBLE | Количество ингредиента | CHECK (quantity > 0) |

**Обоснование:** Составная первичный ключ (id_product, id_ingredients) гарантирует уникальность комбинации продукта и ингредиента.

#### Таблица Customers

Информация о клиентах магазина.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_customer | INTEGER | Уникальный идентификатор клиента | PRIMARY KEY |
| name | CHAR(50) | Имя клиента | NOT NULL |
| phone | CHAR(11) | Телефон клиента | NOT NULL, UNIQUE |

**Обоснование:** Уникальное ограничение на поле phone предотвращает дублирование записей об одном клиенте.

#### Таблица Sale

Заголовки заказов/продаж.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_sale | INTEGER | Уникальный идентификатор продажи | PRIMARY KEY |
| id_customer | INTEGER | Ссылка на клиента | FOREIGN KEY → Customers |
| date_sale | TEXT | Дата продажи | DEFAULT CURRENT_DATE, NOT NULL |
| comment | TEXT | Комментарий к заказу | |

**Обоснование:** Дата по умолчанию устанавливается в текущую, что упрощает создание записей.

#### Таблица Magazine_Sales

Детализация продаж по товарам.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_sale | INTEGER | Ссылка на продажу | PRIMARY KEY, FOREIGN KEY → Sale |
| id_product | INTEGER | Ссылка на продукт | PRIMARY KEY, FOREIGN KEY → Products |
| quantity | INTEGER | Количество товара | CHECK (quantity > 0) |
| price | DOUBLE | Цена на момент продажи | CHECK (price > 0) |

**Обоснование:** Составной первичный ключ позволяет хранить несколько позиций в одном заказе. Сохранение цены на момент продажи важно для исторической точности (цены могут меняться).

#### Таблица Occasions

Справочник праздников и событий.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_occasion | INTEGER | Уникальный идентификатор праздника | PRIMARY KEY |
| occasion_name | CHAR(50) | Название праздника | NOT NULL |

**Примеры записей:** "День рождения", "Свадьба", "Новый год", "8 Марта".

#### Таблица Product_Occasion

Связь между продукцией и праздниками.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_product | INTEGER | Ссылка на продукт | PRIMARY KEY, FOREIGN KEY → Products |
| id_occasion | INTEGER | Ссылка на праздник | PRIMARY KEY, FOREIGN KEY → Occasions |

**Обоснование:** Позволяет ассоциировать товары с подходящими событиями (например, свадебный торт → "Свадьба").

#### Таблица FilterEvents

Логирование действий пользователей по фильтрации товаров.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id | INTEGER | Уникальный идентификатор события | PRIMARY KEY, AUTOINCREMENT |
| session_id | TEXT | Идентификатор сессии пользователя | NOT NULL |
| filters | TEXT | JSON-строка с применёнными фильтрами | NOT NULL |
| results_count | INTEGER | Количество результатов после фильтрации | |
| created_at | DATETIME | Время события | DEFAULT CURRENT_TIMESTAMP |

**Обоснование:** Эта таблица является ключевым элементом системы аналитики. Она позволяет:
- Отслеживать, какие фильтры используют пользователи;
- Анализировать популярность различных критериев выбора;
- Выявлять товары, которые часто попадают в результаты поиска;
- Оптимизировать ассортимент на основе реального поведения пользователей.

#### Таблица Calorie_Level

Классификация по уровням калорийности.

| Поле | Тип данных | Описание | Ограничения |
|------|-----------|----------|-------------|
| id_level | INTEGER | Уникальный идентификатор уровня | PRIMARY KEY |
| range | INTEGER | Диапазон калорий | |

### ER-диаграмма

Связи между таблицами можно представить следующим образом:

```
Category (1) ────< (N) Products
Difficulty_Level (1) ────< (N) Products
Products (1) ────< (N) Product_Ingredients >──── (1) Ingredients
Products (1) ────< (N) Product_Occasion >──── (1) Occasions
Customers (1) ────< (N) Sale
Sale (1) ────< (N) Magazine_Sales >──── (1) Products
```

### Нормализация

База данных спроектирована в третьей нормальной форме (3NF):

1. **1NF**: Все поля атомарны, нет повторяющихся групп.
2. **2NF**: Все неключевые поля полностью зависят от первичного ключа.
3. **3NF**: Нет транзитивных зависимостей неключевых полей.

## 2.2. Архитектура системы

### Общая архитектура

Система построена по принципу трёхзвенной архитектуры:

```
┌─────────────────┐      HTTP/REST      ┌─────────────────┐     SQL      ┌─────────────────┐
│   Frontend      │ ◄─────────────────► │    Backend      │ ◄──────────► │   Database      │
│  (Web Client)   │                     │   (FastAPI)     │              │    (SQLite)     │
└─────────────────┘                     └─────────────────┘              └─────────────────┘
```

**Компоненты:**

1. **Frontend (клиентский уровень)**:
   - Веб-интерфейс для покупателей;
   - Административная панель для сотрудников;
   - Работает в браузере пользователя.

2. **Backend (серверный уровень)**:
   - Обработка HTTP-запросов;
   - Бизнес-логика;
   - Валидация данных;
   - Взаимодействие с базой данных;
   - Генерация ответов в формате JSON.

3. **Database (уровень данных)**:
   - Хранение всей информации о системе;
   - Обеспечение целостности данных;
   - Выполнение SQL-запросов.

### Структура Backend

Backend-приложение организовано следующим образом:

```
main.py                 # Точка входа, определение маршрутов API
BD_CANDY_SHOP.bd        # Файл базы данных SQLite
requirements.txt        # Зависимости Python
amvera.yml              # Конфигурация деплоя
```

**Основные модули кода:**

1. **Модели данных (Pydantic)**:
   - AdminLogin — данные для авторизации администратора;
   - FilterEvent — событие фильтрации;
   - OrderItem — позиция заказа;
   - OrderRequest — полный заказ.

2. **Маршруты API (Endpoints)**:
   - Публичные (для клиентов);
   - Защищённые (для администраторов).

3. **Вспомогательные функции**:
   - get_db() — получение подключения к базе данных;
   - verify_admin_token() — проверка токена администратора.

### Структура Frontend

Frontend состоит из следующих основных страниц:

1. **Главная страница (Каталог)**:
   - Список товаров;
   - Панель фильтров;
   - Корзина.

2. **Страница оформления заказа**:
   - Форма контактных данных;
   - Итоговый состав заказа;
   - Кнопка подтверждения.

3. **Административная панель**:
   - Страница входа;
   - Список заказов;
   - Детали заказа;
   - Аналитические дашборды.

## 2.3. Проектирование API

### RESTful архитектура

API спроектировано в соответствии с принципами REST:

- **Ресурсо-ориентированность**: Каждый endpoint представляет собой ресурс (продукты, заказы, аналитика).
- **Использование HTTP-глаголов**: GET для получения, POST для создания.
- **Stateless**: Каждый запрос содержит всю необходимую информацию.
- **Единый формат ответов**: JSON.

### Документация API

FastAPI автоматически генерирует интерактивную документацию:

- **Swagger UI**: доступен по адресу `/docs`;
- **ReDoc**: доступен по адресу `/redoc`.

### Описание endpoints

#### Публичные endpoints (без авторизации)

| Метод | Путь | Описание | Параметры |
|-------|------|----------|-----------|
| GET | `/` | Приветственное сообщение | — |
| GET | `/api/products` | Получение списка товаров | occasions, ingredient_groups, no_nuts, no_gluten, no_dairy, vegan, no_aroma, sort |

## 2.4. Проектирование пользовательского интерфейса

### Принципы проектирования

При разработке интерфейса соблюдались следующие принципы:

1. **Юзабилити**: Минимальное количество кликов для выполнения целевых действий.
2. **Консистентность**: Единый стиль всех элементов интерфейса.
3. **Адаптивность**: Корректное отображение на различных устройствах.
4. **Обратная связь**: Визуальное подтверждение действий пользователя.
5. **Доступность**: Учёт особенностей пользователей с ограничениями.

### Цветовая схема

Выбрана цветовая схема, ассоциирующаяся с кондитерскими изделиями:

- **Основной цвет**: Тёплые оттенки (розовый, кремовый, шоколадный);
- **Акцентный цвет**: Для кнопок действия (зелёный для подтверждения);
- **Фон**: Светлый для лучшей читаемости.

### Адаптивный дизайн

Интерфейс адаптируется под различные размеры экранов:

- **Desktop (>1024px)**: Полноценная версия с боковой панелью фильтров;
- **Tablet (768-1024px)**: Фильтры скрываются в выпадающую панель;
- **Mobile (<768px)**: Одноколоночная раскладка, карточки товаров на всю ширину.
